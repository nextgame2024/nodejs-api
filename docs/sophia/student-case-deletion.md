# Permanent case deletion and case controls

The related-case card uses a green restore/history icon for archived cases, smaller 32px desktop buttons (44px touch targets), and a permanent Delete action with native confirmation. Archived cases sort last on the server before pagination and stay last when related pages merge in the browser. Eligible linked-invoice actions and Create remain visible but disabled for archived/deleting cases; write endpoints continue enforcing the case guard.

`POST /cases/:caseId/delete` requires `{recordVersion,confirmed:true}`, an Idempotency-Key, and cases.manage/payments.prepare/payments.read_all. Deletion preserves the student account and identity links while any other case remains (including archived cases). Deleting the last case also removes the student login/profile, student links and student-owned authentication records. Shared provider projections remain as unlinked terminal facts. It deletes this case's documents, analysis/reviews, offer courses/fees/instalments, draft batches/exports, upload/replacement/delete receipts, schedule, invoice links, checklist, activity and case row. A minimal tenant-scoped deletion receipt survives, with provider targets cleared, so lost responses remain retryable. Provider document files are retained with their contact; this action does not delete external document files.

Before provider changes, the API verifies permissions, optimistic version, case access, live work leases, invoice identities and unsettled statuses. Unconfirmed invoice creation receipts must be reconciled first; permanent deletion cannot abandon unknown provider invoices. Shared invoices and contacts mapped to another student are refused. Draft/submitted invoices become DELETED; unpaid, uncredited AUTHORISED invoices become VOIDED. Paid/credited/protected invoices prevent deletion. Every known invoice is read before the first write. Independent invoice work uses three workers, drains in-flight work on failure and uses stable provider keys.

**Contact rule:** excluding the case being deleted, if any other case exists for the same student, retain active contacts and the student account. Archived cases count as remaining cases and must be explicitly deleted one by one. Archive the student's known billing/document contacts and remove the student account only when deleting the last case. The student profile lock serializes this decision with creation/restoration; unfinished deletion prevents a new case/restore from invalidating the decision.

A durable deletion claim freezes the target case. Preflight failures before provider mutation unfreeze it. Once mutations may have started, it remains read-only until Delete is retried and completes. Retries re-read actual provider statuses rather than resending confirmed deletions; expired leases are reclaimable and concurrent initial requests cannot steal a live lease. All provider writes complete before local purge. When enabled, encrypted temporary analysis copies are removed before purge. Queued analysis/discovery excludes deleting cases; checklist automation does not advance them.

Migration 113 adds the deletion receipt, deleting marker and archive-order index. Local purge uses one narrowly scoped SECURITY DEFINER function with an explicit tenant/job/token check and fixed search_path. Runtime retains its normal non-BYPASSRLS role and receives no table DELETE grants. Case activity remains append-only except its FK cascade when that case is permanently purged; no global trigger disabling is used. Unknown future FK dependencies fail the local transaction rather than cascading across unrelated data.

Deploy migrations `113_student_case_deletion.sql` and `114_delete_last_case_student.sql` through the owner migration runner **before** the Runtime API and frontend. Existing migration 112 is required. Migration 114 repairs students left with zero cases by an earlier completed permanent deletion; ordinary no-case students and students with any remaining case are preserved. No production migration, provider mutation or deployment was performed during implementation.

Follow-up: remove the student after deleting their last case (2026-11-01)

The original case-only purge retained the account, leaving the student register with a “No cases” row. Migration 114 wraps the existing provider-confirmed case purge and removes the now-orphaned student in the same transaction. Completed deletion retries also run this cleanup, without repeating external mutations. The migration's scoped repair applies the same function to previously completed deletion receipts so existing leftovers such as TEST4 do not require an inaccessible case page.

Cleanup requires a tenant-scoped completed receipt, exact account/company/profile mapping and zero remaining cases. It refuses unresolved invoices and unknown referencing business rows (including cascade foreign keys). It removes student-owned identity/contact/candidate links and authentication children, unlinks terminal provider facts, then deletes profile/login. Student audit remains append-only except its FK cascade from this approved profile deletion. Runtime receives function EXECUTE only; direct DELETE privileges and RLS boundaries are unchanged. Counters and unrelated accounts remain intact. Confirmation explains that deleting the last case also deletes the student record.

Follow-up: archived sibling cases still retain the contact (2026-11-01)

The final rule replaces the former “all remaining cases archived” condition with “no remaining cases.” Each deletion removes only the selected case and its eligible invoices. The account remains active while any sibling case exists, including archived siblings. Existing interrupted deletion plans are checked again on retry and obsolete contact-archive targets are removed when siblings remain. The confirmation states that contact archiving and student removal happen only on the last case.
