# Payment Operations & Reconciliation

**Decision requested · Open For Australia · 27 November 2026**

Build a payment operations workspace **inside Business Manager → Payments and Control**, backed by a dedicated workflow in the existing Student Operations pack. Give staff one review screen for a receipt, its student and instalments, what the college is owed and what PTY has collected. Keep Xero authoritative for each organisation's accounting balances. A verified receipt can advance a time-sensitive case while its bank reconciliation is pending.

This review comprises this design, the [official API capability matrix](payment-operations-xero-capabilities.md) and the [phased backlog and validation plan](payment-operations-delivery.md). The MVP is an AUD pilot for verified TRUST bank receipts, including partials and pre-feed receipts. It includes visibility and safe exception intake for the other scenarios. Later phases complete those workflows. Production grants, college agreements, postings and bank evidence have not been inspected.

## 2. Architecture decision

| Decision factor | A · Extend the invoice register and connector directly | B · Dedicated workflow behind the existing register |
|---|---|---|
| Maintainability | Fewer files initially. An invoice becomes the parent for bank observations, Stripe payouts and direct-college proofs, including those without invoices. | Adds a payment domain with explicit relationships. Existing connector, identity, schedule, commission and invoice services retain their responsibilities. |
| Effort | Fastest read-only invoice enhancement. Supporting unidentified receipts and many-to-many splits later requires rebuilding the centre of the workflow. | More initial schema and permission work. A read-only slice ships independently and each posting command has a defined boundary. |
| Scale | Cross-org joins and repeated provider lookups are tempting within an invoice detail request. | Indexed local projections support inbox searches. Job-based ingestion and scoped refresh control API cost. |
| UX | Staff start from an invoice or organisation. Hard to find a payment whose owner is unknown. | Staff start from the incoming movement or deadline. They can see both permitted organisations and open the existing invoice detail. |
| Operational complexity | Smaller initial footprint, increasingly intertwined retry, approval and email states. | More explicit jobs/states to monitor, independent recovery for each accounting write, notification and attachment. |
| Reuse | Strongly tied to an OFA invoice export. | Configurable sources, organisation roles and accounting policies. Student-specific rules stay inside the pack. |

**Recommend B.** Retain the existing register and routes. Add a lazy-loaded Operations view in that module. Run the new domain services within the Student Operations pack, using the established connector and shared worker. One physical deployment can host both. A second integration stack, a generic core financial engine or a new hosted service would add cost before the pilot establishes demand.

### Boundaries and interfaces

| Boundary | Proposed contract |
|---|---|
| Angular → Runtime | Under the authenticated Student Operations API add paged operations, summary and detail reads, candidate review, evidence association, verify, prepare, approve and handoff commands. Example proposed relative routes: `GET /payment-operations?cursor=…`, `GET /payment-operations/{id}`, `POST /payment-operations/{id}/proposals`, `POST /payment-proposals/{id}/approvals`. Actions include expected revision and idempotency key. Return accepted operation ID, status and safe reason for blocked actions. |
| Source adapters → observations | Each adapter supplies source/account identity, stable external ID when available, booking/effective date, observed time, direction, currency, amount and evidence pointer. An imported statement row, a manager's bank verification and a Xero payment can describe one movement. Preserve each observation. |
| Domain → Xero | Tenant-bound connector resolves credentials, account and scopes. One approved command targets one organisation and one operation. Persist a durable claim and frozen payload before network I/O. Read back provider IDs and balances. |
| Storage and jobs | Transactionally commit local changes with queued work. Claim short leases, fence writes with lease token/version, commit progress per page/command, release locks during network calls. Jobs have independent receipts for accounting, evidence publication and email. |
| Accounting → UI | Separate rows and totals for bank movements, processor balances, Xero documents and operational obligations. Consolidate navigation across permitted organisations. Never sum TRUST receipts and PTY commission as agency revenue. |

### Data model

Proposed logical entities below can share existing physical tables where the listed constraints hold. Every row carries Sophia customer scope. Every Xero reference resolves through an immutable tuple of customer, connection, external tenant, resource type and provider ID. Enforce composite foreign keys and allowed organisation roles in the database and server. Store the connection/role at the time of an action so reassignment cannot silently redirect historical work.

| Entity / relationship | Key fields, existing links and constraints |
|---|---|
| Financial policy version | Customer, organisation pair, college/contract where applicable, effective interval, settlement method, allowed channels/accounts, currency, verification/approval rules, recognition trigger, signed-off-by. Pin revision on proposals. Unconfigured paths open a policy exception. |
| Payment observation → movement | Ingest key unique per customer, source, source account and provider event/row ID. Amount, sign, dates, original ref, masked payer, source type, verifier, evidence. A canonical movement has many observations, one channel and owner; record cross-source links with rationale. Direct-to-college uses college as destination, with TRUST cash marked inapplicable. Identical manual rows produce duplicate candidates, never a destructive merge. |
| Xero resource projection | Reuse invoice/contact tables. Add typed payment, bank transaction and relevant batch/transfer facts keyed by the external tuple, with account, amount/currency, direction, updated time, import provenance, deletion and nullable reconciliation state. Unique PaymentID across standalone/batch/detail views within its tenant. One movement may link to several accounting objects. |
| Movement allocation → invoice/schedule → line intent | Many-to-many signed allocations in invoice currency, approved revision, source/target amounts and FX if applicable. Local line intent points to a specific LineItemID or immutable source-line/version; preserve evidence of purpose and explicitly unassigned amount. Keep candidate, reserved, posted/imported, reversed states distinct. |
| College obligation and settlements | Link case, approved offer/instalment, BM college and schedule, due date, settlement method, policy and optional same-tenant ACCPAY. Many settlement applications with payer (student/agency), amount, confirmation/evidence and optional Xero account payment. Separate partial refunds and corrections. |
| Commission entitlement and applications | Link college, case/instalment and rule snapshot, original and revised calculation, tax components, eligibility evidence and earned date. Reference current PTY export or reviewed historic receivable. Track actual receipts, amounts settled by approved offset, and unrecovered balance independently. For direct business with no TRUST export, add a separately validated PTY draft origin referencing confirmed educational settlement. Preserve current paired-export constraints. |
| Student credit and applications | Movement and student/contact, same-org OverpaymentID, remaining credit, first-seen date, age, applications/refunds and evidence, unresolved amount and resolution path. Separate unresolved cash from an approved credit and keep original history after closure. |
| Stripe source/account, balance entries, payout, payout members | Merchant account + mode + external ID keys, owning Xero tenant/account, charge/intent, balance transaction, currency, signed gross/fee/net, available date, payout ID and expected/observed arrival. Many member entries per payout, including negative adjustments. Store provenance for provider vs manually reviewed links. |
| Match proposal / candidate / approval | Movement, candidate or split, scoring version and contribution details, competing score, decision reason, source snapshot, invoice revision and expiry. Each approval binds actor, role, organisation, amount, account, evidence hash, policy revision and exact command hash. |
| Operation receipt / outbox / exception | Unique business intent across users/jobs, frozen payload, step-specific provider key, current claim, status, external IDs and safe error. Exception stores reason, owner, next action, due time, evidence and resolution. A separate operation is required for each authorised leg. |
| Evidence, communication and audit | Reuse case document ID or private financial evidence with explicit ACL, content hash/version, MIME, size and retention class. Many-to-many evidence links. Message records frozen recipient list, subject/body template version, approved attachment versions/hashes, provider message ID, send attempts and callback events. Append-only financial events link before/after facts, actor, reason, origin, correlation ID and receipts. |
| Sync/reconciliation observations | Extend per-connection sync runs with resource cursor, committed watermark, last success/full check, gap and retry state. Every reconciliation observation records object/account/leg, value, evidence source and time. Store staff confirmation independently of Xero flags. |

**Financial invariants.** Use integer minor units with an explicit currency exponent at movement/allocation boundaries and exact decimals for provider rates, unit prices and the existing numeric(18,4) projections. Store Xero originals and compare validated currency-quantised totals. One movement's applied amounts + reserved amounts + available remainder equal its verified amount, counted once per allocation revision. Excess, unassigned cash and refunds remain visible. Line intent plus unspecified line coverage equals the invoice allocation. An imported payment cannot count again as a local proposal. Two parallel approvers must compete for the same remaining balance under a row lock/version check. Local assignments never overwrite Xero AmountDue. On a provider change invalidate outstanding approvals, retain superseded versions and raise a difference when facts disagree.

### Independent states shown to staff

| Dimension | Values and evidence for progression |
|---|---|
| Identity and verification | Unidentified → suggested → confirmed identity. Unverified → evidence received → bank/processor/college verified or disputed/reversed. Record who, when and how. |
| Accounting per org/leg | Inapplicable / unposted → proposed → approved → sending → posted or linked to existing. Unknown outcome, rejected, reversed and blocked are explicit. A DRAFT has its own Xero status. |
| College | Due → partial → settled by agency or confirmed paid directly, with amount, period and evidence. A refund can reopen it. Sending a request or receipt adds a communication event only. |
| Commission | Eligibility pending / ineligible → calculated → earned under policy → requested/invoiced → part collected → collected or settled by approved offset. Track cash received separately even if the claim is fully discharged. |
| Bank reconciliation | Inapplicable, unknown, pending, staff-reported complete, Xero-reported reconciled. Record source and as-of time, surface later reversals/conflicts. An invoice's paid date is insufficient evidence. |
| Stripe and mail | Stripe: succeeded → pending/available → payout scheduled/paid → bank observed; failure, refund and dispute are independent events. Mail: draft → approved → submitted → delivered/bounced/unknown, with college acknowledgement recorded independently. |

## 3. Business and accounting decisions

| Fact pattern | What staff can establish | Decision required before accounting automation |
|---|---|---|
| Student pays TRUST | Actual agency bank receipt, approved invoice application, remaining student obligation. A college due date follows its contract. | Accountant chooses receipt account, timing, gross/net remittance and whether college debt is recorded as a bill or an operational payable. PTY cash stays unchanged until supported by a separate event. |
| TRUST remits gross | Approved college settlement for the gross contractual amount. PTY can have a separate unpaid commission claim. | Confirm contract basis, taxes, earning event, invoice/collection dates. A college remittance does not collect commission. |
| TRUST remits net | Link actual net movement, contractual gross and authorised offset amount. Confirm the college accepts that combination as discharge. | Accountant documents any inter-entity receivable/payable and how PTY claim is discharged. An offset is distinguishable from PTY cash. Later actual transfers receive their own evidence and approval. |
| Student pays college | Verified external settlement against course/instalment. Where a TRUST receivable exists, display its outstanding Xero balance and an accounting exception until dealt with. | Determine whether the original TRUST invoice applies, needs a correction, or a documented non-bank treatment. If no TRUST entry is required, retain an operational memorandum with evidence. No simulated bank receipt or automatic write-off. |
| Stripe collected, bank pending | Processor balance, fees and scheduled payout are observable separately. Funding a college due today requires actual available, permitted funds. | Confirm merchant owner, fee bearer, settlement account, existing Xero automation, who may fund a shortfall, clearing design and tax. Never authorise a transfer based on future payout alone. |
| Small credits, refunds and changes | Attribute exact residual to the student and keep an ageing trail, contact attempts, entitlement and refund evidence. | Confirm beneficial ownership, refund authority, retention and applicable unclaimed-money regime with the accountant and where needed legal adviser. Amount or age alone cannot authorise income recognition. Queensland rules depend on the holder and jurisdiction. [Queensland Public Trustee](https://www.pt.qld.gov.au/other-services/unclaimed-money/how-to-lodge-unclaimed-money) |

**Commission eligibility needs a separate fact check.** For Australian overseas-student recruitment, the Department of Education describes restrictions on commissions for onshore transfers and exceptions, including acceptance for enrolment by 31 March 2026 and specified progression cases. A configured college rate or a simple onshore label does not establish eligibility. Ask the client and its adviser to identify applicable cohorts, acceptance and course history, exceptions and required evidence. A non-eligible or undecided claim cannot be requested, invoiced or collected through the new workflow. [Department of Education guidance](https://www.education.gov.au/esos-framework/changes-legislative-framework-overseas-students)

**Discovery evidence to request.** Ask the finance lead for one anonymised case per workflow, a gross and a net remittance, relevant college agreements, an example adjustment/refund, each entity's account/currency/lock-date mapping, a Stripe payout itemisation matched to the bank, and the approved college email template. Have the accountant mark each expected entry or “no entry” per entity. Have operations nominate preparers, approvers, funding limits, evidence standards, due dates and statement import format. Record effective dates and decisions against the policy version. These inputs gate the affected writes and can be gathered while read-only design is reviewed.

## 4. Matching, synchronisation and approval

**Deterministic candidate selection.** First resolve customer, destination organisation/account or direct-college channel, currency and direction. Reject cross-tenant candidates, voided/deleted documents and incompatible currencies. Search existing payments, batches, credits and reservations **before** proposing new postings. Already paid invoices remain candidates for linking a historical payment, even though they are ineligible for a new payment. Build candidates from indexed invoice references, student and college IDs, known payer relationships, case/offer/instalment and bounded date/amount windows. Preserve the original reference and the normalised tokens. A missing reference must not prevent manual lookup across the permitted student's outstanding invoices.

| Proposed starting score | Evidence and guardrail |
|---|---|
| Up to 50 for identifiers | Exact, unique invoice number or payment reference linked to one instalment 50. Exact unique student ID 35. Take the strongest result from this family; repeated tokens add nothing. An exact provider PaymentID already imported identifies an existing record and bypasses scoring. |
| Up to 25 for identity | Verified payer→student/sponsor or explicit confirmed enrolment mapping 25; independently matched name 10. A parent paying for two students creates ambiguity. Count only evidence independent of the identifier above. |
| Up to 15 for amount | Outstanding or scheduled amount exactly 15; documented partial or excess consistent with the stated purpose 8. Amount alone never raises a candidate above low. |
| Up to 10 for context | Within agreed due-date window 5, independent college/course or prior confirmed history 5. Contradictory student ID, currency, organisation or occupied source movement blocks approval until resolved. |

Proposed pilot bands: **exact** requires a unique, consistent stable identifier and independently verified identity/purpose; **high** requires at least 75/100, two independent families including identity/reference, and a 15-point lead; **review** for 45–74 or a smaller lead; **unidentified** if there is no credible candidate. An exact identifier with contradictory evidence goes to investigation. These are ranking points, not probabilities. Show each contribution, counterevidence, next-best alternative and residual. With an AUD 3,000 receipt, exact instalment reference + confirmed sponsor + documented partial + date = 88. Two equal AUD 3,000 receipts with only amount and date score 20 each. Neither can be posted from the suggestion.

Support several receipts per invoice via remaining balances. For combined receipts, prefer explicit remittance splits across invoices belonging to the identified payer, recheck all totals, and cap search breadth. If references are absent, allow manual search/split with reason; never accept a unique-looking subset sum as evidence of identity. Store accepted/rejected candidates by rule version. Measure top-choice precision, ambiguous rate and median review time on independently labelled synthetic or appropriately authorised cases. A later text-extraction experiment should run blind against that baseline on permitted data, abstain on conflicts and produce evidence a reviewer can verify. Xero prohibits training or fine-tuning models with API-derived data. No AI match can approve a financial write. [Xero developer terms](https://developer.xero.com/xero-developer-platform-terms-conditions)

**Sync and recovery.** Backfill per organisation and resource with bounded pages, resumable cursors and consistent source identity. Imported history is read-only until reviewed. Use modified-since where the endpoint documents it, overlapping watermarks and deduplicated upserts. Where incremental filters or event coverage are insufficient, use bounded lookbacks, periodic full checks and targeted reads of pending objects. Delete/void events close projections without erasing local evidence. A missing row on an incomplete page/full run cannot close a case. Store last attempted, last successful incremental and last complete sweep separately. Current register “reconciliation” sync verifies import consistency; give it a different UI label from bank reconciliation.

Verify provider signatures over the exact raw body, persist a tenant-routed inbox with version-aware envelope parsing, acknowledge after durable capture, then hydrate through the connector. Treat webhooks as hints and coalesce by object/version; deduplicate by provider event ID or stable envelope key where supplied. Unknown tenants never enqueue financial actions. Add a bounded priority lane for explicit operator checks/unknown outcomes without starving the existing overnight imports. Normal page loads read locally. Display queue lag, source age, error class, pending unknowns, reconciliation discrepancies and retries by tenant, with redacted correlation IDs. Enforce shared tenant quota/cooldown, Retry-After and jitter for recoverable throttling/5xx. An expired/revoked grant pauses affected work and directs an administrator to Company. Validation and lock-date errors require correction. [Token handling and concurrency](https://developer.xero.com/documentation/best-practices/data-integrity/managing-tokens/)

**Posting contract.** An operations user prepares the exact target, evidence and split. An authorised approver confirms the entity, bank/clearing account, date and effect after step-up. Proposed pilot policy uses a different preparer and approver for Xero writes, refunds, offsets and adjustments. The client must confirm staffing/delegation or choose a documented control before activation. Revalidate permissions, current source evidence, enabled connection, invoice and eligible account, remaining balance, competing reservations, manual Xero payments, period and approved policy immediately before dispatch. Any changed financial fact invalidates the approval. The provider can still change between the read and write: handle provider rejection or unexpected read-back as a conflict. Never infer authorisation from a menu entitlement.

Give each business action a durable unique key independent of UI retries, user and worker. Also send a globally unique Xero Idempotency-Key with identical method/body for transient retries. Xero retains these keys for **six minutes**. On a lost reply, recover by known ID or using the saved bounded account/document/date/amount/reference and exact payload evidence. After expiry use a new provider key only if absence is established and the business claim still owns the write. Ambiguous or eventually consistent results stay in review. Preserve successful TRUST legs if PTY or mail fails; retry only the unresolved leg. No automatic compensating journal. [Xero idempotency](https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/)

**Evidence privacy.** Restrict list projections, case detail, evidence download, exports and actions separately. Enforce customer RLS, scoped document permissions and access per organisation for both joins and aggregate counts. Assigned advisors see permitted status only. Store bank/Stripe secrets server-side, rotate with the existing secret-management pattern, log safe IDs, and exclude raw statements, tokens and student identifiers from telemetry. Encrypt new private evidence, bind paths and short-lived access to the customer, validate file type/size and scan before preview, external attachment or email. Keep original source immutable under the agreed retention schedule. An uploaded statement requires account, currency, period and uploader; duplicate files and overlapping exports retain row lineage. Where a bank supplies no stable row ID, use statement context and occurrence index to detect exact replay and review cross-file collisions.

**Concurrent work in Xero.** A Sophia lock cannot prevent someone in Xero or another connected app from posting during the same interval. Assign one posting owner per channel/account for the pilot. A manual handoff reserves the case for the Xero operator and disables Sophia dispatch until a read-back or a reviewed release. If a competing writer still posts, link both external IDs, freeze the affected allocation, show the excess and require an authorised correction. Test both a pre-existing payment and a genuinely simultaneous external write.

## 5. End-to-end workflows

### 1 · AUD 3,000 received into TRUST against AUD 3,500

1. A bank-confirmed deposit or approved bank CSV creates an observation. The operator opens the receipt and sees student/course, outstanding TRUST invoices and linked PTY commission. Retrieve current invoice, known payments and the current college obligation.
2. Match reference, payer/student relationship, expected instalment and amount. Check legal entity, currency, approved invoice, exact outstanding balance and previous postings. The operator selects AUD 3,000 for tuition. If the payer did not specify tuition, leave the line purpose unassigned.
3. The approver sees “Record AUD 3,000 on TRUST invoice” with the destination account and resulting AUD 500 due. Claim the allocation and call `PUT /Payments` for the invoice only. If Xero already has it, attach the existing PaymentID. A DRAFT goes to the existing invoice authorisation process.
4. Read back PaymentID, AmountDue and flag. Save posting receipt, local line intent and approval. Materials remain AUD 500 due in the stated example. Display college amount/due date from contract and commission from its own rule/claim. A partial student payment alone cannot discharge either.
5. An amendment, duplicate candidate or uncertain response puts just that action into review. A human finishes Find & Match once the statement line exists. The final record can be verified and posted while reconciliation remains pending.

### 2 · Paid Directly to College

1. Student supplies a receipt. Staff record the payment type, date, amount, currency, institution, reference, case/offer and evidence. Check payee, duplicate, agreed instalment, permitted evidence access and whether TRUST invoiced it.
2. Staff review and, if needed, send the evidence to the college through the approved communications flow. Record a separate acknowledgement/confirmation with who, when, amount and document. A discrepancy leaves the claim pending or partial. Sending a message cannot confirm receipt of funds.
3. Apply the confirmed amount to the local educational obligation. Show TRUST cash and bank reconciliation as inapplicable. If Xero still shows an open TRUST invoice, display both balances and assign the accountant an exception. Keep the original financial facts visible until an approved correction is observed.
4. Calculate the eligible commission using the reviewed offer, current applicable rules and contract, snapshot the result and confirm the PTY college recipient. Reuse an existing linked PTY invoice. If the current exporter requires a TRUST invoice that never existed, keep the claim local or link a manually verified PTY invoice until a separate approved direct-college export path exists.
5. On approval, prepare a PTY ACCREC draft via `PUT /Invoices` only where policy calls for it. Track request date, due date and receivable separately. When PTY actually receives money, link its existing payment or approve `PUT /Payments` against the authorised PTY invoice, then hand off reconciliation in PTY. A failed commission step leaves the confirmed college settlement intact.

### 3 · Bank verified Monday, Xero feed Tuesday

1. The manager observes a booked TRUST credit in authorised online banking, records account, bank reference, amount, transaction date, time of verification and evidence. A pending transfer or student screenshot alone cannot satisfy the bank-verification policy.
2. Match and check for an existing Xero payment. Under approved pre-feed policy an authorised reviewer can record the payment against an approved TRUST invoice on Monday, omitting the reconciliation flag. Otherwise keep it verified locally. Independently review the college deadline, actual available funds, payee and approval; staff execute any EFT in their bank.
3. Tuesday's bank CSV or authorised bank integration may supply a corroborating observation. Link it to Monday's movement. Where only the Xero feed is available, staff find the statement line in Xero. The handoff shows the original account, date, amount, reference and existing PaymentID. If Monday was local-only, choose exactly one posting path: create/link in Xero or complete the approved Sophia command, then refresh before the other path is allowed.
4. Staff select the existing accounting transaction in Find & Match and approve reconciliation in Xero. Refresh the known payment/batch flag. Save provider status and timestamp or keep staff attestation with “awaiting Xero confirmation” if unavailable. If reconciliation is undone later, reopen the exception. Duplicate Tuesday imports, grant loss and a lost Monday response cannot create another receipt. [Xero Find & Match](https://central.xero.com/0/guide/a5B3m00000F5CItEAN/keep-your-bank-records-accurate-and-up-to-date)
